# WSL2 Codex 环境决策与案例记录

## 决策记录

### D-01：目标开发环境

- **问题**：继续修补原生 Windows sandbox，还是迁移到 WSL2？
- **选择**：WSL2 Ubuntu 24.04，仓库位于 Linux 文件系统。
- **否决方案**：继续依赖 WindowsApps alias、WinGet 用户私有路径和宿主 keyring。
- **理由**：WSL2 原生 `python3`、uv、Git 和 gh 路径可稳定解析，临时 Git 可直接运行。
- **可逆性**：部分可逆；Windows 仓库可保留，但正式工作流以 WSL2 为目标。
- **回滚触发器**：WSL2 无法可靠连接、性能不可接受或关键工具不兼容。

### D-02：仓库路径

- **选择**：`/home/<user>/code/tracequant`。
- **否决方案**：`/mnt/c`、`/mnt/d` 等 Windows 挂载盘。
- **理由**：避免跨文件系统权限、大小写、file mode 和 I/O 语义差异。
- **可逆性**：可逆；通过受控 commit/patch 后重新克隆。
- **回滚触发器**：Linux filesystem 空间不足或损坏。

### D-03：Python 入口

- **选择**：系统诊断使用 `python3`，项目使用 `uv run python`。
- **否决方案**：安装 `python-is-python3` 或创建全局软链接。
- **理由**：当前入口已满足系统与项目职责，不引入额外全局状态。
- **可逆性**：可逆。
- **回滚触发器**：上游工具明确且不可配置地要求裸 `python`。

### D-04：uv 版本策略

- **选择**：固定 `uv 0.12.1`，与 CI 一致。
- **否决方案**：跟随本地最新版本。
- **理由**：避免环境与 CI 漂移，保证可复现验证。
- **可逆性**：可逆，但升级必须同时修改 CI、文档和重新验证。
- **回滚触发器**：已确认的安全或兼容性问题要求升级。

### D-05：GitHub 认证

- **选择**：在 WSL 内使用独立、可撤销的 gh 登录。
- **否决方案**：复制 Windows 凭据目录或读取宿主 keyring。
- **理由**：凭据边界清晰，可撤销，不需要把宿主完整认证材料带入 WSL。
- **可逆性**：可逆；`gh auth logout`。
- **回滚触发器**：scope 过宽、凭据泄漏或登录失效。

### D-06：网络路径

- **选择**：正式远程操作使用“已验证代理 + approval”。
- **否决方案**：把无代理直连作为正式依赖。
- **理由**：无代理场景仅部分成功，`github.com` 与 Git remote 超时。
- **可逆性**：可逆；代理变化后重新诊断。
- **回滚触发器**：代理不可用、证书错误或网络策略改变。

### D-07：权限策略

- **选择**：记录 approval 边界，最终最小权限 Rules 延后到独立 Task。
- **否决方案**：为使诊断全部变绿而配置宽泛 Rules。
- **理由**：环境 Task 的目标是测量边界，不是消除安全门禁。
- **可逆性**：可逆。
- **回滚触发器**：后续 Rules 审计发现授权过宽或命令匹配不稳定。

## 案例记录

### C-01：GitHub 认证失败与恢复

- **类型**：failure / recovery
- **触发**：初始 `gh auth status` 没有已登录主机，HTTPS Git fetch 提示凭据失败。
- **时间线**：初始诊断失败 → 在 WSL 内完成 gh 登录与 Git 集成 → repo/Issue/PR 只读成功 → fetch 成功但需要 approval。
- **诊断**：网络和 TLS 正常，失败域是 WSL 内认证而非 GitHub 可达性。
- **响应**：采用 WSL 独立、可撤销 gh 登录，不复制 Windows 凭据。
- **结果**：GitHub 只读与正式 fetch 可用。
- **通用经验**：网络、认证和 Git metadata 写入应分开诊断。

### C-02：uv 版本漂移与恢复

- **类型**：failure / recovery
- **触发**：本地 uv 与 CI 固定版本不一致。
- **诊断**：功能验证可通过，但可复现性不满足。
- **响应**：升级并固定为 `0.12.1`。
- **结果**：工具版本与 CI 对齐，项目验证通过。
- **通用经验**：本地“能运行”不能替代版本契约。

### C-03：WSL2 改善工具可见性但不消除 approval

- **类型**：unexpected
- **触发**：预期迁移后多数正常开发命令可直接运行。
- **观察**：`/tmp` 临时 Git 直接成功；正式 Git metadata、用户 uv cache 和 GitHub 网络仍需 approval。
- **诊断**：操作系统边界与 Codex sandbox 边界彼此独立。
- **结果**：环境判定为 `ready-with-gaps`，而不是失败或完全免审批。
- **通用经验**：平台迁移不能替代权限模型设计。

### C-04：裸 `python` 不存在但开发环境完整

- **类型**：unexpected
- **触发**：`command -v python` 无输出。
- **观察**：`/usr/bin/python3` 和 `uv run python` 均为 Python 3.12.3；全部项目验证通过。
- **诊断**：缺失的是命令别名，不是 Python 运行时。
- **响应**：系统脚本使用 `python3`，项目命令使用 `uv run`。
- **结果**：不安装额外 alias。
- **通用经验**：应验证实际入口和职责，而不是只检查一个命令名。

### C-05：可逆 GitHub 写探针

- **类型**：success
- **触发**：需要验证 GitHub 写 scope，但不能留下 Issue、PR 或持久变更。
- **响应**：创建唯一临时 remote ref，读取并立即删除，随后核验 remote ref 和 PR 均不存在。
- **结果**：写权限通过且无残留，命令需要 approval。
- **通用经验**：权限诊断应优先使用唯一、可逆、可核验清理的对象。

### C-06：无代理访问仅部分成功

- **类型**：unexpected
- **触发**：临时移除代理变量进行直接网络诊断。
- **观察**：`api.github.com` 成功，`github.com` 和 `git ls-remote` 超时。
- **诊断**：不能把单一 API 成功推广为完整 GitHub 工作流无需代理。
- **响应**：正式路径保留代理 + approval，无代理标记为 `partial`。
- **通用经验**：网络能力需要按 endpoint 和协议分别验证。
